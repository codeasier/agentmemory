# v0.9.30-patch upgrade record

This worktree (`v0.9.30-patch`, base commit `8bf0c82` = upstream tag `v0.9.30`) replaces the
fork's `v0.9.29-patch` line. The line carries **only the fork-only deltas**, re-implemented
(never cherry-picked) on the new base: 19 commits, each naming the commit it was ported from as
`[ported from <sha>]`.

Companion record: [`iii-022-migration-validation.md`](iii-022-migration-validation.md) — the
retired `migrate/iii-0.22.1` branch's historical evidence, kept with corrections.

## Why the base moved

- `v0.9.29-patch` was upstream `v0.9.29` plus **46 local commits**, and almost all of them were
  backports of fixes upstream has since shipped natively in `v0.9.30` (tip of that line:
  `38d2e30`).
- `migrate/iii-0.22.1` added **10 further commits** that moved the engine pin to 0.22.1. That
  move is native in `v0.9.30` too. The branch is retired and pushed to `origin` as a record
  (tip `b5ee97a`).
- Re-applying either line onto `v0.9.30` would mean porting patches into the release that already
  contains them. The new line keeps only what upstream does not have.

### Vector index precision and bookkeeping

| Commit | Ported from | What it does |

### Incremental graph extraction

| Commit | Ported from | What it does |
| --- | --- | --- |
| `957546b` | `b60c7ab` | The session record carries a matched `graphExtractedAt` / `graphExtractedDigest` watermark and the stop handler dispatches only observations above it. The digest is an order-independent fingerprint of the already-extracted ids, so a late-compressed or evicted observation re-sends the session rather than skipping data; mixed-precision timestamps compare by `Date.parse` epoch. The dispatch is an awaited, success-confirmed `mem::graph-extract` (not a void fire), so the watermark only advances for a batch the extraction confirmed. `AGENTMEMORY_GRAPH_INCREMENTAL_EXTRACT=false` restores whole-session dispatch. |
| `64d5d44` | `e5f8213` | A failed extraction (provider error or partial LLM failure) stamps `graphExtractRetryAt = now + AGENTMEMORY_GRAPH_EXTRACT_RETRY_MS` (default 300000); stops inside that window skip extraction entirely — the gate is checked before the observation batch is computed, so a cooling-down session does no digest work either. A successful pass clears the cooldown in the same `kv.update` that advances the watermark. |
| `b8da411` | `6222a7e` | A failed extraction used to wait for the *next* `event::session::stopped`; when the failing stop was the session's last, nothing ever retried. The graph path moves into `runGraphExtraction()`, which arms an in-process per-session wake-up timer on failure and re-arms after each failed retry. A boot sweep re-arms sessions whose retry window outlived the process, concurrent attempts per session are serialised, and a session with nothing left to extract no-ops. |
| `9df7c1c` | `2172459` | Future-stamped observations count as part of the extracted half and the persisted watermark is clamped to wall-clock time (a future stamp could pin it above every later real timestamp); the stale-watermark log is throttled per session (60 s). Also pins the extract-then-consolidate ordering: reflection reads the graph, so the consolidation fan-out must not start against a half-written one. The audit-sweep and observe-counter halves of the reference are handled elsewhere (upstream retention, `ccf7d1b`). |
| `9b46c85` | `54569d3` | `mem::graph-extract` returns `success: !llmError` instead of `true` whenever any node was persisted, so a partial extraction is not reported as clean; `mem::migrate` tallies the observations per migrated session instead of writing `observationCount: 0`; `POST /agentmemory/graph/build` counts whatever the batch reports instead of gating the totals on `success`. |

### Cutover and live state

1. The service was stopped with the **old** build's `ExecStop`. This means there is **no
   cross-version shutdown-proof validation** on this cutover: the new worker-side proof
   (`80577fd`) was never exercised by the stop that produced the store the new build loaded.
2. The new drop-in, the prestart guard and the `/usr/bin/agentmemory` symlink were installed, and
   the service was started.
3. Live after cutover: `/agentmemory/livez` 200, `/agentmemory/health` 200
   `{"status":"healthy"}` with zero alerts once the boot rebuild finished, viewer 200, and the
   same index numbers as the baseline (67471 BM25 documents / 76345 vectors / 153 buckets).
4. A `post_tool_use` observation was captured by the installed dsh hook within a minute of the
   start, i.e. the pre-existing hook scripts are wire-compatible with the new server. The new
   capture inbox reported 0 pending / 0 dead.
